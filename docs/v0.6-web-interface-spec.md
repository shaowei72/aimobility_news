# v0.6 — Searchable Web Interface: Product Specification

_Status: agreed, 2026-11-05 (all section 10 decisions made). Scope: core features A1–A3, B1–B3, D1–D2._

---

## 1. Purpose

The pipeline already collects, scores and summarises articles every day, and since v0.4 it stores everything in `output/db/news.db`. What is missing is a good way to **use** that history. Today the options are a dated `digest-*.md` file, a WhatsApp message, or `reader.py` writing yet another Markdown file.

The v0.6 web interface gives the curator **one place to read, find and judge** what the pipeline has collected:

1. **Read**: a better daily experience than a Markdown file: summary, "why it matters", scores and the original link, in one view.
2. **Find again**: every stored article and AI Daily Brief story, by keyword, date, source and score.
3. **Trust**: see why each article was published or dropped, so sources and scoring can be improved.

### 1.1 Non-goals for v0.6

- No natural-language questions, semantic search or generated analysis (v0.7 and v0.8).
- No replacement of the WhatsApp digest as the delivery channel.
- No writes: no labelling, collections, settings editing or pipeline runs from the UI (later releases; see section 9).
- No accounts, multi-user support or public hosting. It runs on the local machine.
- No metrics dashboard (D3–D4); it comes after the core, alongside priority 2 in the checkpoint.

### 1.2 User

One user: the **curator** (project owner). They read the digest each evening, share selected items to WhatsApp, and maintain the sources and scoring rules. They are technical, so showing scores, model names and run IDs is fine, but the default view should read like a news product, not a database browser.

## 3. Data foundation

### 3.1 Source of truth

The web app reads **`output/db/news.db` only**, never the `digest-*.md` or `whatsapp-*.txt` files. The database holds everything the files contain plus what they leave out (unpublished articles, the three domain scores, reasons, the exact text scored, model and prompt versions).

| Need | Tables |
|---|---|
| What a run published, and the status of every article it saw | `runs`, `digest_items` |
| Article metadata and text | `articles` (`title`, `source`, `published_at`, `summary`, `content`) |
| Scores and reasons, and the text the model saw | `scores` (`transport_*`, `ai_*`, `gis_*`, `total_score`, `text_label`, `text`, `scored_by`, `error`) |
| Digest summary | `summaries` (`title_en`, `summary`, `why_it_matters`, `one_liner`, `error`) |
| AI Daily Brief episodes and stories | `aidb_episodes`, `aidb_story_sets.result` (JSON from `build_stories()`) |

### 3.2 Access rules

- **Read-only.** Open the database with `file:...?mode=ro` (as `reader.py` does), never with `db.connect()`, which runs the schema and migrations. This makes the app safe to keep open while the pipeline or a backfill writes.
- **Pipeline runs only** for briefings: `runs.kind LIKE 'pipeline%'` (includes `pipeline (imported)`). Backfill and import runs supply AI Daily Brief content and scores but are not briefings.
- **Reuse the reader's rules** where they exist: content day in local time, the latest run wins when an article appears in several runs, the preferred story-set model (`openai` first), and story URLs built as `aidailybrief.story_articles()` builds them. Move the shared queries into a module used by both `reader.py` and the web app, rather than copying them.

### 3.3 Key definitions

| Term | Definition |
|---|---|
| **Briefing** | The set of items a pipeline run published (`digest_items.published = 1`), in digest order: ITS qualified, then ITS notable ("Also notable"), then AI Daily Brief headlines. |
| **Briefing of a day** | The **latest** pipeline run started on that local date. Earlier same-day runs (re-runs; e.g. 2026-11-03 had six) are reachable from a run selector. |
| **Content day** | The day an item belongs to in the archive and search: an ITS article's `published_at` in local time (else its run's date); an AI Daily Brief story's episode date. |
| **Status** | `digest_items.digest_status`: `qualified`, `notable`, `ai headline`, `below threshold`, `scoring failed`. Shown with the published flag. |
| **Near-miss** | An article that was not published but came close: `notable` and not published (cut by `TOP_RANKED`), or `below threshold` with a total within a set margin of `MIN_TOTAL_SCORE` (`NEAR_MISS_MARGIN`, default 4: totals 7–10 against a threshold of 11), or any domain score at `NOTABLE_MIN_*` minus 1. Thresholds are read from the run's `runs.settings`, falling back to `config.py`. |

### 3.4 Search index

FTS5 is available (SQLite 3.39.4 in the project's Python).

- The index lives in a **separate file**, `output/db/search.db`, built from `news.db`. This keeps `news.db` read-only for the app and avoids schema changes to the pipeline database.
- It is **rebuilt automatically** when `news.db` is newer than the index (checked on startup and before each search), and on demand with a CLI command. At the current size (388 articles, 53 episodes) a full rebuild takes well under a second; it can become incremental if needed.
- **Indexed documents:**
  - ITS article: title, English title, feed summary, digest summary, why it matters, full text (`articles.content`), source.
  - AI Daily Brief story: headline, summary, key points, episode title and lead.
- **Two tokenizers**, because Gasgoo and the future Chinese feeds are in Chinese:
  - `unicode61` with `remove_diacritics`, for English words and short queries such as "AI", "EV" or "LTA".
  - `trigram`, used when the query contains CJK characters (Chinese has no spaces between words). Trigram needs at least 3 characters; shorter CJK queries fall back to `LIKE`.
- **Ranking:** `bm25()` with field weights (title > summary and why it matters > full text), with "most recent" available as an alternative sort.

## 4. Information architecture

```
┌────────────────────────────────────────────────────────────────────┐
│  AI Mobility News    [ Briefing ]  [ Search ]        [ search… ⏎ ] │
└────────────────────────────────────────────────────────────────────┘
   /                      → Briefing, latest run
   /briefing/2026-11-05   → Briefing of a day (latest run that day)
   /briefing/2026-11-05?run=2026-11-05+17:58:09   → a specific run
   /briefing?from=2026-11-01&to=2026-11-05        → catch-up range (A3)
   /archive               → calendar or list of days with briefings (B3)
   /search?q=…&source=…&from=…&to=…&min_total=…&status=…&section=…  (B1, B2, D1)
   /article/<id>          → ITS article detail (A2, D2)
   /aidb/<date>           → AI Daily Brief episode
   /aidb/<date>/<story>   → AI Daily Brief story detail (A2)
```

Every page has a stable URL, so a filter or an article can be bookmarked. The search box in the header is on every page.

## 5. Feature specifications

### 5.1 Briefing view (A1, B3)

**Goal:** read the day's briefing as published, quickly and comfortably.

**Layout:**

```
Daily Briefing — Thursday 5 November 2026            ◀ 4 Nov   6 Nov ▶
Run 20:45 · 8 ITS articles · 0 AI headlines · openai:gpt-6.1-sol   [run ▾]

INTELLIGENT TRANSPORTATION SYSTEM (ITS)
 1  Title (English title if the original is Chinese)
    Gasgoo Intelligent Connected Vehicles · 5 Nov 09:12 · qualified · 24  [T4 A4 G0]
    Summary paragraph…
    Why it matters: …
    Read original ↗    Details →
 …
ALSO NOTABLE
 …
AI DAILY BRIEF
 Episode title — lead
 1  Headline · AI 4/5 · 12:30–18:05 · Listen / read ↗   Details →
 …

▸ Not published in this run (37)   ← collapsed; see 5.5
```

**Requirements:**

| # | Requirement |
|---|---|
| BR-1 | `/` shows the briefing of the latest pipeline run. |
| BR-2 | Items appear in digest order and grouping: ITS qualified, "Also notable", AI Daily Brief headlines. The order is by total score, as in `ranking.select_for_digest()`. |
| BR-3 | Each ITS item shows: title (and English title when it differs), source, published time (local), status, total score and the three domain scores as a compact badge, summary, why it matters, and a link to the original that opens in a new tab. |
| BR-4 | If a summary is missing, show why: "Summary failed: …" (from `summaries.error`), or "Published before summaries were stored" for imported runs. |
| BR-5 | AI Daily Brief items show the headline, AI score, time window, summary (expandable to key points) and the episode link. When a run published no AI headlines, show the episode, if there is one for the date, with its stories collapsed and the note "No stories reached the AI headline threshold". |
| BR-6 | Previous and next day navigation skips days with no pipeline run. |
| BR-7 | A run selector lists all pipeline runs of the day (time, number published, code version) when there is more than one. |
| BR-8 | The header line shows the run time, counts per section, and the scoring model from `runs.settings`. |
| BR-9 | Each item has a "Copy link" action that copies the original URL. This is enough for sharing; a "copy as WhatsApp line" action using `summaries.one_liner` is optional. |
| BR-10 | Days before 2026-11-03 have no ITS data in the database. The archive shows AI Daily Brief-only days for them and states that ITS history starts on 2026-11-03. |

**Archive (`/archive`, B3):** a month calendar or list of days. Each day shows the number of ITS items published and AI Daily Brief stories, and whether it has an ITS briefing or AI Daily Brief only. Clicking a day opens its briefing.

### 5.2 Catch-up view (A3)

**Goal:** after a few days away, see what was published without opening each day.

| # | Requirement |
|---|---|
| CU-1 | `/briefing?from=…&to=…` shows the published items of the latest run of each day in the range, grouped by day, newest first. |
| CU-2 | Quick ranges: "Last 3 days", "Last 7 days", "Since my last visit". The last visit is stored in the browser's local storage, not the database. |
| CU-3 | An article published by several days' runs appears once, under its first day, marked "also in 6 Nov". This is the same story deduplicated by URL; same-story matching across URLs is for v0.7. |
| CU-4 | A compact mode shows one line per item (title, source, score), for scanning; items expand in place. |
| CU-5 | The range is limited to 31 days per page. |

### 5.3 Article detail (A2, D2)

**Goal:** everything known about one ITS article on one page, including why it was or was not published.

**Sections, top to bottom:**

1. **Header:** title, English title, source, published time, original link, and status badges for the latest run.
2. **Digest summary:** summary and why it matters, the summarising model and time. If more than one summary exists, the latest is shown and older ones are listed.
3. **Scoring panel (D2):**
   - The three domain scores as bars from 0 to 5, each with its **reason** text.
   - The total and how it is calculated: `total = (T + 1) × (A + G + 1) − 1 = 24`. Show it against `MIN_TOTAL_SCORE` ("13 points above the threshold of 11" / "1 point short").
   - The **classification explained** in plain language, following `ranking.classify_article()`, e.g. "Not qualified (total 10 < 11). Notable because AI score 3 ≥ 3. Not published: 8 higher-ranked articles filled the TOP_RANKED slots."
   - Model (`scored_by`), code version, prompt hash (short), scored at, and whether the score was **reused** from an earlier run with an identical prompt.
   - **What the model saw:** `text_label` (full text or summary only) and the word count, with the exact `scores.text` behind an expander. A warning shows when the model saw only the feed summary.
   - Scoring error, if any.
4. **Run history:** one row per pipeline run that saw the article: run time, status, published, section, total. This shows when it first appeared and whether its status changed.
5. **Score history:** when the article was scored more than once (another model or rubric), one row per score: model, code version, T/A/G, total. Useful for comparing OpenAI with Ollama later.
6. **Article text:** feed summary and the longest full text stored (`articles.content`), collapsed by default.

| # | Requirement |
|---|---|
| AD-1 | Reachable from the briefing, search results and run history. |
| AD-2 | The classification explanation uses the thresholds stored with the run (`runs.settings`), so old runs are explained by the rules in force at the time, not today's. |
| AD-3 | The "not published because of TOP_RANKED" explanation needs the rank within the run. Compute it from the run's `digest_items` and `scores`. |
| AD-4 | Text in Chinese is shown as is; the English title and summary from `summaries` come first when present. |

### 5.4 AI Daily Brief story detail (A2)

| # | Requirement |
|---|---|
| AS-1 | Episode page (`/aidb/<date>`): title, lead, episode link, the model that built the story set, and all stories with headline, AI score, section, time window and status. |
| AS-2 | Story page: headline, summary, key points, time window, link to the episode at that point, and the scoring panel (as in 5.3, with the AI score emphasised, and the AI headline rule `AI ≥ AIDB_HEADLINES_MIN_AI_SCORE`). |
| AS-3 | When an episode has several story sets (e.g. OpenAI and Ollama on 2026-10-27 and 2026-10-29), show the preferred one (`openai`) and offer the other as a switch. |

### 5.5 Search and filters (B1, B2, D1)

**Goal:** find any stored item by keyword and narrow it by facets.

**Layout:**

```
[ robotaxi                                   ] [Search]
Section: (•) All ( ) ITS ( ) AI Daily Brief
Date:    [2026-10-01] – [2026-11-05]   Source: [ All sources ▾ ]
Status:  [x] Published [x] Notable [x] Below threshold [ ] Scoring failed
Score:   Total ≥ [  ]  Transport ≥ [ ]  AI ≥ [ ]  GIS ≥ [ ]
Presets: Published only · Near-misses · Summary-only scoring · Chinese sources
Sort:    (•) Relevance ( ) Newest ( ) Highest total

42 results
 Title · Source · 3 Nov · published (qualified) · 24 [T4 A4 G0]
   …snippet with **robotaxi** highlighted…
```

| # | Requirement |
|---|---|
| SR-1 | **Keyword search** over the index in 3.4. Support phrases ("autonomous bus"), `OR`, and exclusion (`-tesla`); show the FTS5 syntax error in plain language if a query is invalid. |
| SR-2 | An empty query with filters is a valid browse ("all Gasgoo articles in October with AI ≥ 4"). |
| SR-3 | **Facets:** section (ITS, AI Daily Brief), content-date range, source (multi-select, with counts), status (multi-select, with "published" as its own facet), minimum total and minimum per-domain scores, scoring text (full text or summary only), model. |
| SR-4 | Each result shows the title, source, content date, status and published flag, score badge, and a **highlighted snippet** (`snippet()`), and links to the article or story detail. |
| SR-5 | Status, published flag and score come from the article's **latest** pipeline run, as in `reader.load_its_rows()`. AI Daily Brief stories that appear only in backfill runs use their latest score and status. |
| SR-6 | **Near-miss preset (D1):** not published, and either `notable` or within the near-miss margin (3.3); sorted by total, highest first. Each result shows "1 point short" or "Notable, cut by TOP_RANKED" in the list itself. |
| SR-7 | Other presets: "Published only", "Summary-only scoring" (`text_label` is the summary, a sign of failed full-text extraction), "Chinese sources". |
| SR-8 | All filters live in the URL query string, so a search can be bookmarked and the back button works. |
| SR-9 | Paging: 25 results per page. |

### 5.6 "Not published" panel on the briefing (D1)

A collapsed panel at the foot of each briefing lists the articles that run saw but did not publish, grouped as: **Notable, not published** (cut by `TOP_RANKED`), **Near the threshold**, **Below threshold**, **Scoring failed**. Each line shows the title, source, total, the T/A/G badge and a one-line reason ("AI 3 → notable; ranked 11th of 8 slots"). It links to the article detail.

## 6. Reading experience

The product strategy calls for a good reading experience. Concretely:

- **Typography first:** a readable serif or humanist sans at 17–18 px, line length about 70 characters, generous spacing; scores and metadata in smaller, muted text so they do not compete with the summary.
- **Calm by default:** the briefing shows summaries and why it matters; scoring detail is one click away, not inline.
- **Light and dark themes,** following the operating system setting.
- **Keyboard navigation:** `j`/`k` next and previous item, `o` open original, `Enter` details, `/` focus search, `[` and `]` previous and next day.
- **Responsive:** usable on a phone browser on the same network. Desktop is the main target.
- **Fast:** each page under 300 ms locally; no client-side framework needed.
- **Chinese text:** fonts with CJK fallback; the English title and summary come first and the original title is shown beneath it.

## 7. Technical approach

| Aspect | Proposal | Reason |
|---|---|---|
| Server | Python **FastAPI** with **Jinja2** server-rendered templates (decided 2026-11-05) | Same language and repo as the pipeline; easy to test; no build step |
| Interactivity | Plain HTML forms and links; **HTMX** (one script) for expanders and in-place filtering, if wanted | Keeps the reading pages light and bookmarkable |
| Styling | One hand-written CSS file (or a classless base such as Pico.css) | Full control of typography |
| Data access | A new `aimobility_news/web/queries.py` (read-only), sharing query helpers with `reader.py` | One definition of "latest run", "content day", story URLs |
| Search | `aimobility_news/web/search_index.py` builds `output/db/search.db` (FTS5, two tokenizers) | Keeps `news.db` untouched |
| Running | `uv run python -m aimobility_news.web` → `http://127.0.0.1:8000`, bound to localhost only | Local, single user |
| Dependencies | Add `fastapi`, `uvicorn`, `jinja2` (and `httpx` for tests) | Small, common |
| Tests | pytest with a temporary database seeded with fixture runs (as `tests/test_db.py` does); route tests through the test client | No API calls, never opens the real `news.db` |

Framework decided on 2026-11-05: FastAPI (decision 1 in section 10).

## 8. Acceptance criteria (v0.6 exit criterion)

v0.6 core is complete when, on the real `news.db`:

1. `/` shows the latest run's briefing, matching the `digest-YYYY-MM-DD.md` of that run item for item (titles, order, sections).
2. Any day since 2026-11-03 can be opened as a briefing, re-runs can be selected, and AI Daily Brief days back to 2026-09-01 appear in the archive.
3. A catch-up range of 7 days shows each published article once.
4. A keyword search returns matches from titles, summaries and full text, in English and in Chinese (a three-character Chinese query on a Gasgoo article), with highlighted snippets.
5. Filters by date, source, status, section and minimum scores work alone and combined, and survive a page reload via the URL.
6. The near-miss preset lists every unpublished `notable` article and every article within the near-miss margin, each with a correct one-line reason.
7. Every article detail page shows the three scores with reasons, the total formula, the scored text and its label, the model and code version, and a classification explanation consistent with `ranking.classify_article()` under that run's thresholds.
8. The app opens `news.db` read-only and works while a pipeline run is writing.
9. Tests pass (`uv run pytest`), including route tests for each view and unit tests for the near-miss and classification-explanation logic.

## 10. Open questions and decisions

1. ~~**Framework**~~ — decided 2026-11-05: **FastAPI** + Jinja2.
2. ~~**Near-miss margin**~~ — decided 2026-11-05: configurable as `NEAR_MISS_MARGIN` in `config.py`, default 4 (totals 7–10 against a threshold of 11), plus any domain score one below its `NOTABLE_MIN_*`.
3. ~~**"Briefing of a day"**~~ — decided 2026-11-05: the **latest** pipeline run of the day; earlier runs stay reachable from the run selector (BR-7).
4. ~~**AI Daily Brief in pipeline briefings**~~ — resolved 2026-11-05, not a bug. The episodes the pipeline runs saw (2026-11-01, 11-02, 11-04) are single-topic deep dives with a "Main episode" section and no "Headlines" section, so each became one story, and those stories scored AI 1–2, below `AIDB_HEADLINES_MIN_AI_SCORE` (3). Such episodes are common (about 1 in 5 in the backfill: 10-07, 10-12, 10-18, 10-23, 10-25). Consequence for BR-5: an empty AI Daily Brief section is a normal state, and the briefing should still show the day's episode and its stories with their scores.
5. ~~**Shared query module**~~ — decided 2026-11-05: refactor `reader.py` to use the shared queries module in v0.6. The module stays standard-library only and read-only, so the reader keeps those properties; it then runs as `python -m aimobility_news.reader` (the direct-path form `python src/.../reader.py` is dropped).
6. ~~**Phone access**~~ — decided 2026-11-05: **localhost only** (`127.0.0.1`) for v0.6. LAN access with an access token can come later.
